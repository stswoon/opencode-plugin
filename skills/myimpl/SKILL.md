# myimpl

Оркестратор. Production-код сам не пишешь. Статус в плане меняешь **только** после `LEAD_PASS`.

```
не сделано (зависимости закрыты)
  → dev (код)
  → qa (матрица приёмки + независимые проверки)
  → lead (ревью кода, тестов и docs/spec)
  → статус: сделано
```

План и статусы: `docs/plan/`. Спека: `docs/spec/`. Схема статусов — skill `myplan`.

Нет поля **Статус** в файле стори → как `не сделано`.

## Допущения и решения

**Допущение** — спека, стори и декомпил молчат, но для реализации нужен выбор (нет числа, поведения, имени контракта).
Агент (dev/qa/lead) на любом этапе возвращает такие места оркестратору с 2–4 вариантами и рекомендацией.

**Допущение пользователя не ждёт:**

1. Выбери первый рекомендованный вариант; если агент не дал рекомендации — ближайший к декомпилу и минимальный по scope.
2. Дай решению ID (`D1`, `D2`, …) и запиши блок в `.cursor/artifacts/decisions.md` (формат ниже).
3. Передай решение агенту как обязательное и в `{{DECISIONS}}` последующих этапов этой стори.
4. Продолжай цикл без остановки.

Агент, вернувший допущение, ждёт решение: продолжай того же агента через `resume` с текстом решения `D…`, не перезапускай с нуля. То же для нестыковки — после ответа пользователя.

**Нестыковка** — прямое противоречие: требования/стори конфликтуют между собой, со спекой, декомпилом или фактическим
кодом, либо самый разумный вариант расходится со спекой. Это стоп-фактор: задай пользователю вопрос в формате skill
`myplan` (где → что не сходится → что зависит → варианты с последствиями → рекомендация) и жди ответ. Ответ запиши как
решение `D…` и передай на текущий этап. По спорному месту цикл не идёт.

Журнал решений — один файл на запуск `.cursor/artifacts/decisions.md`; пишет только оркестратор, агенты — никогда.
Новый запуск дописывает новый раздел, прежние не стирает.

```markdown
# Решения myimpl — <дата время>

## D1 — <короткое имя> (Sxx, этап Dev|QA|Lead)
- Где: `docs/plan/Sxx-*.md` / `docs/spec/...:N` / `файл:строка`
- Суть: что было неясно или в чём противоречие
- Решение: <вариант> — почему; источник: рекомендация агента | выбор оркестратора | ответ пользователя
- Альтернативы: Б) <что было бы иначе в поведении/коде/тестах, плюсы и минусы>; В) <…>
- Расхождение со спекой: нет | есть (`файл/раздел`, был вопрос пользователю)
- Затронуто: <файлы>
```

Пока по допущению или нестыковке нет блока `D…` в журнале, стори дальше по циклу не идёт.

## Выбор сторей

1. Прочитай `docs/plan/README.md` и все `docs/plan/S*.md`.
2. Пользователь назвал ID — только они (если зависимости `сделано`).
3. Иначе **одна волна**: все `не сделано`, у которых каждая зависимость `сделано`, и папки не пересекаются (как «Параллель» / «Папки» в стори).
4. Нет таких — напиши, что заблокировано и чем, остановись.
5. Пользователь сказал «все волны» — повторяй волны, пока не кончатся готовые или пока агент не упрётся.
6. Волна стартует с чистого дерева: `git status` не должен содержать незакоммиченных файлов сторей. Грязное дерево — сначала закоммить законченные стори, потом начинай волну.

Не тащи в одну волну стори, которые правят одни и те же файлы (`src/shared` ломают только явно и по одной). Волна — не больше 4 сторей; UI-цепочки (`hud.ts`, `styles.css`, `en.json`) — строго последовательно.

## Цикл одной стори

Порядок жёсткий: сначала Dev, потом QA по **готовому** коду, потом Lead.

1. **Dev** — Task `subagent_type: dev`, промпт [prompt-dev.md](prompt-dev.md). `{{FEEDBACK}}` в первом заходе: «нет»; при повторе — путь к `.cursor/artifacts/bug-report-Sxx.md` или `review-notes-Sxx.md` и список активных блокеров (полный текст не копируй).
2. **QA** — Task `qa`, промпт [prompt-qa.md](prompt-qa.md). Пока Dev не сдал код, QA не запускай. В первом заходе `{{PREVIOUS_QA_REPORT}}` и `{{PREVIOUS_LEAD_REPORT}}`: «нет»; при повторе — путь к отчёту и активные блокеры/замечания одной выжимкой.
3. Проверь QA gate сам: существует `.cursor/artifacts/bug-report-Sxx.md`, в нём есть решение, строка на каждый пункт приёмки и на каждое решение `D…` этой стори, команды и ручной UI-сценарий, если он обязателен. `QA_PASS` без этих свидетельств не передавай Lead — верни тому же QA на дополнение отчёта.
4. **Lead** — Task `lead`, промпт [prompt-lead.md](prompt-lead.md). Пока нет доказательного `QA_PASS`, Lead не запускай. `{{QA_REPORT}}` — путь к `.cursor/artifacts/bug-report-Sxx.md` + решение; `{{PREVIOUS_LEAD_REPORT}}` в первом заходе: «нет», при повторе — путь и активные замечания. Полные тексты отчётов не копируй: Lead читает файлы сам.
5. `LEAD_PASS` → в файле стори и в таблице README поставь `**Статус:** сделано`, затем закоммить файлы скоупа стори (`src/`, `tests/`, `docs/`, план и артефакты этой стори) сообщением `Sxx: <краткое> (LEAD_PASS)`. `git add` — только по путям стори, чужие незакоммиченные изменения не захватывай.
6. Провал:
   - `QA_FAIL` → Dev с `.cursor/artifacts/bug-report-Sxx.md` (путь + список активных блокеров); Dev обязан добавить регрессионный тест на исправимый дефект. Затем снова QA (дельта-прогон по правилам агента) → Lead.
   - `LEAD_FAIL` → Dev с `.cursor/artifacts/review-notes-Sxx.md` (путь + активные замечания); затем снова QA по дельта-правилам, включая регрессии, → Lead.
   - больше 3 петель по одной стори — стоп, отдай пользователю блокеры, статус не меняй.

Несколько сторей волны: Dev можно запустить **параллельно** (несколько Task в одном сообщении), если папки разные. QA/Lead — тоже параллельно после сдачи своей стори, не раньше.

## Промпты Task

Роли: агенты `dev`, `qa`, `lead` (регистрируются плагином).

| Кто | `subagent_type` | Промпт волны |
|-----|-----------------|--------------|
| Разработчик | `dev` | [prompt-dev.md](prompt-dev.md) |
| QA | `qa` | [prompt-qa.md](prompt-qa.md) |
| Lead | `lead` | [prompt-lead.md](prompt-lead.md) |

`model`: `inherit`. В промпт передавай полный текст стори, решения `D…` этой стори из `.cursor/artifacts/decisions.md` (плейсхолдер `{{DECISIONS}}`; нет решений — «нет») и **пути** к отчётам предыдущих этапов с выжимкой активных блокеров — у subagent нет истории чата, но файлы он читает сам. Полные тексты прошлых отчётов не копируй. Не подменяй роли сторонними агентами (например, React-ориентированным `dev-fe`).

Артефакты разных сторей не перезаписывай:

- QA: `.cursor/artifacts/bug-report-Sxx.md`
- Lead: `.cursor/artifacts/review-notes-Sxx.md`
- Решения: `.cursor/artifacts/decisions.md` (общий журнал запуска; ведёт только оркестратор)

## После волны

Пользователю:

- какие стори стали `сделано`, какие остались `не сделано`, блокеры, что открывать (`npm run dev` и т.п.);
- **сводка решений**: по каждому `D…` — что решено и почему, альтернативы с подробным описанием (что было бы иначе, плюсы и минусы), стори и файлы; путь к `.cursor/artifacts/decisions.md`. Решений не было — скажи об этом прямо;
- приглашение: «скажи „поменяй D<N> на вариант …“ — переделаю затронутые стори»;
- хеши коммитов закрытых сторей (`Sxx: <краткое> (LEAD_PASS)`), каждая стори уже закоммичена.

## Изменение принятых решений

Пользователь по сводке просит поменять решение («поменяй D2 на вариант Б») → оркестратор:

1. правит блок `D<N>` в `.cursor/artifacts/decisions.md`: новое решение, пометка «изменено по запросу пользователя, <дата>», прежний вариант сохраняется;
2. передаёт новое решение как `{{FEEDBACK}}` Dev затронутых стори и прогоняет цикл заново (Dev → QA → Lead);
3. стори, уже помеченные `сделано`, на время переделки возвращает в `не сделано`, после `LEAD_PASS` — снова `сделано`.

Новые решения в сводке нумеруются со следующего свободного ID.

## Не делать

- Не вызывать `analyst` и не переписывать план целиком (это `myplan`).
- Не ставить `сделано` после одного Dev без QA и Lead.
- Не начинать волну на грязном дереве и не оставлять закрытую стори незакоммиченной.
- Не принимать `QA_PASS` без полной матрицы приёмки и фактических свидетельств.
- Не запускать QA «на будущее» параллельно с первым Dev той же стори.
- Не реализовывать стори, чьи зависимости ещё `не сделано`.
- Не принимать нестыковку или расхождение со спекой молча — это вопрос пользователю.
- Не передавать стори дальше, не записав принятое решение блоком `D…` в `.cursor/artifacts/decisions.md`.
- Не менять и не удалять прежние решения журнала самому — только по запросу пользователя.
